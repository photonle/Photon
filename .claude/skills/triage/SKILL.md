# Triage

GitHub numbers issues and pull requests in one sequence, so resolve a bare `#42` first:
`gh api repos/photonle/Photon/issues/42 --jq .pull_request` prints `null` for an issue and an object
for a PR, which gets a [sanity check](#checking-a-pull-request) instead of triage.

Every comment or issue posted to the tracker during triage **must** start with this disclaimer:

```
> *This was generated by AI during triage.*
```

## Stages

Every open issue carries one Stage: `New`, `Needs Information`, `Awaiting Review`, `Triaged` or
`Blocked`. One with no Stage predates the field and is `New`. One that won't be actioned is closed
with a reason instead. [.claude/docs/issue-tracker.md](../../docs/issue-tracker.md) is the source of
truth for how issues move between Stages and what each type needs before it counts as triaged; types
themselves are chosen against [Choosing a type](../github-issues/SKILL.md#choosing-a-type), and the
calls that set them are in [the `github-issues` skill](../github-issues/SKILL.md). Flag a type,
Stage or field that contradicts the others, or a transition that looks unusual, and ask before
proceeding.

## Invocation

Requests arrive in natural language, such as:

- "Show me anything that needs my attention"
- "Triage the backlog" or "auto" ([auto mode](#triage-the-backlog-auto-mode))
- "Let's look at #42"
- "Check PR #296"
- "What's triaged and ready to pick up?"

## Show what needs attention

Run [scripts/buckets.sh](scripts/buckets.sh) from the repo root and present what it prints: counts,
and a one-line summary per item. With no arguments it prints the buckets that need triage, oldest
first; `--help` lists the others, including `triaged` for what's ready to pick up. Let the maintainer
pick.

## Triage the backlog (auto mode)

Showing the buckets stays the default. When the maintainer asks for auto mode instead ("auto",
"triage the backlog", "triage a backlog item"), pick for them:

1. Run `scripts/buckets.sh --oldest` to get the oldest issue in each default bucket.
2. Take them in bucket order: `new`, then `needs-info`, skipping an empty bucket. "Triage a backlog
   item", singular, takes only the first issue found.
3. Triage each through [Triage a specific issue](#triage-a-specific-issue). Step 3 still waits for
   direction on every issue: types, fields, comments and closes are public.
4. Before each next issue, say which bucket it comes from and how many are left.

When every picked issue is done, rerun the script and offer the next round rather than starting it.

## Triage a specific issue

1. **Gather context.** Read the full issue (body, comments, type, fields, labels, author, dates).
   Read any prior triage notes and check which of their questions the reporter has since answered,
   so the issue picks up where the last pass left it. Explore the codebase using the vocabulary of
   `CONTEXT.md` where it exists, respecting ADRs under `docs/adr/` in the area. Many open issues are
   years old: check whether the code they describe still exists in the shape they describe.

   For a request for new or changed behaviour (anything but a bug, which restores behaviour already
   intended), run three checks:

   - (a) **Redundancy**: search for an existing implementation of the requested behaviour by domain
     concept, not just the request's wording, and report where you looked. If found, it's already
     implemented, and closes as completed (step 5).
   - (b) **Prior rejection**: read `.out-of-scope/*.md` and surface any that resembles this request.
   - (c) **Fit**: hold it against the project's stated scope in
     [CONTRIBUTING.md](../../../.github/CONTRIBUTING.md#general) and against
     [docs/design-constraints.md](../../../docs/design-constraints.md). A request that can only be
     built by breaking a design constraint is out of scope as asked: recommend the close, or the
     reshaped request that keeps the constraint.

2. **Verify the claim.** Before recommending anything, check that the claim holds up. For a bug,
   reproduce it from the reporter's steps, or find the faulty code path. Record what happened:
   confirmed (with code path), failed, or insufficient detail (a strong `Needs Information`
   signal). A confirmed verification makes a much stronger brief.

   When the bug sits in code a GLuaTest suite can reach, spawn the
   [`qa-tester`](../../agents/qa-tester.md) agent to pin it: pass the code path and the reporter's
   steps, and ask for one case named after the bug, run red against `development`. A case that goes
   red is the confirmed reproduction. It is evidence, not the fix: carry its name and what it
   asserts into the brief as an acceptance criterion, then revert the suite change so the worktree
   stays clean. When the tester reports the case unrun or green, say so; neither confirms the bug.

3. **Recommend.** Tell the maintainer the type, Priority, Effort (none for a Feature) and Stage you
   recommend, with reasoning, plus the verification result, the check verdicts, and a brief
   codebase summary relevant to the request (including whether it's already implemented). Wait for
   direction.

4. **Grill (if needed).** A Feature skips this step: its grilling is `/grill-to-spec`'s, after
   triage. If any other request needs fleshing out, call the Skill tool with "grilling" and grill it
   into shape a round of questions at a time, sharpening domain terms and updating `CONTEXT.md` and
   ADRs inline as decisions land.

5. **Apply the outcome:**
   - **`Triaged`**: post a brief comment ([BRIEF.md](BRIEF.md)) where the type needs one, then set
     the type and, in one POST, Stage, Priority and Effort. An Epic or Initiative takes its children
     as sub-issues instead of a brief. A Bug counts as verified with the faulty code path named or a
     red case; an in-game reproduction is welcome but not required.

   Whatever the outcome, once the type is set remove the superseded labels the issue templates
   added ([Labels](../github-issues/SKILL.md#labels)).
   - **`Awaiting Review`**: comment which decision the issue is waiting on and whose it is.
   - **A Feature that passes the checks** goes to `Awaiting Review`, never `Triaged`: post a
     [condensed brief](BRIEF.md#condensed-brief-feature), set the Priority, then the Stage. The
     decision it waits on is the grilling, which `/grill-to-spec` runs into a full spec.
   - **`Needs Information`**: post triage notes (template below).
   - **Close**: comment why, then close with the reason that matches
     ([Closing an issue](../github-issues/SKILL.md#closing-an-issue)):
     - **Already implemented**: point to where it lives and close as completed. Do **not** write to
       `.out-of-scope/` (that KB is for *rejected* requests, not built ones).
     - **Rejected (bug)**: give a polite explanation, then close as not planned; say so when the
       reason is that verification failed.
     - **Rejected (feature request)**: write to `.out-of-scope/`, link to it from a comment, then
       close as not planned ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
     - **Duplicate**: name the other issue in the comment, then close with `--duplicate-of`.
   - **`New`**: set it. Optional comment if there's partial progress.

## Checking a pull request

Pull requests aren't triaged: they carry no type or Stage. A PR named to `/triage` gets a sanity
check instead, reported to the maintainer, who decides what happens to it. Check each of these and
report whether it holds, with the evidence:

1. **Up to date.** How many commits the head branch is behind `development`, and whether it still
   merges cleanly (`gh pr view <n> --json mergeable,mergeStateStatus`).
2. **Still needed.** Whether `development` has fixed or built the same thing since the PR was
   opened. Search for the behaviour by domain concept, not the PR's wording, and read the commits
   that have landed on the files it touches since its merge base. If it closes an issue, check that
   issue is still open.
3. **Still in scope.** Whether it matches an `.out-of-scope/` entry, breaks a design constraint, or
   an ADR or decision that landed after it was opened contradicts it.
4. **Checks.** The CI state on its head commit: `gh pr checks <n>`.

End with one verdict: ready for review, needs a rebase, superseded (name what superseded it), or out
of scope. Posting any of it on the PR is the maintainer's call; a comment, if asked for, starts with
the AI disclaimer like any other.

## Needs-information template

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

Capture everything resolved during grilling under "established so far" so the work isn't lost.
Questions must be specific and actionable, not "please provide more info".
